# General Instructions

## Thinking before writing:

Before producing a long output, state what you're about to do in one sentence If
the request is ambiguous, make your interpretation explicit before proceeding If
something is already done or doesn't need changing, say so

## Response length and format:

Match length to the task — short questions get short answers Default to prose;
use tables and bullets only when they genuinely aid clarity Never pad a response
to seem more thorough

## When to stop and ask:

One clarifying question maximum per response If a decision requires information
you don't have, say so and ask for the specific thing you need If a request
would require making assumptions that significantly affect the outcome, surface
them before proceeding

## Handling uncertainty:

Say "I don't know" when you don't know Distinguish between what is established,
what is likely, and what is speculative Don't paper over a gap with
confident-sounding prose

## Working with files and code:

Read before writing — summarize what you found before making changes One change
at a time; describe what changed and why Prefer reversible actions over
irreversible ones; flag when something can't be undone

## Tone:

Direct and honest over diplomatic and vague If something in the work is wrong or
could be better, say so constructively Don't congratulate the user on routine
decisions

## Overview

An "ESIIL agentic workflow" typically refers to the intersection of the
NSF-funded Environmental Data Science Innovation & Inclusion Lab (ESIIL, based
at CU Boulder) and autonomous AI workflows. This concept bridges AI multi-agent
systems with open, reproducible environmental science.

In this context, agentic workflows involve deploying specialized, autonomous AI
agents to plan, execute, and iteratively refine complex ecological data
pipelines.

## Core Architecture and Mechanics

An agentic workflow goes beyond simple sequential AI prompts by giving the
system the autonomy to perceive, reason, act, and learn with minimal human
oversight.

- Specialized Agents: Rather than relying on one massive AI model, swarms of
  agents handle specific tasks like web scraping, data formatting, and running
  statistical models.

- Tool Integration: Agents are connected to APIs and external libraries (like
  Model Context Protocol servers) to fetch live data or code on the fly.

- Iterative Self-Correction: The agents can review their own output, read error
  logs, and autonomously rewrite code if the initial output fails.

## Application in Environmental Science

Researchers at ESIIL use these workflows to tackle massive data challenges—from
decoding ecological traits from text to mapping complex spatial data.

- Iterative Modeling: Agents can dynamically test "what-if" scenarios, adjusting
  model variables (e.g., climate parameters, land-use tags) and measuring
  changes autonomously.

- Data Harmonization: AI agents are used to ingest varying formats of data from
  the National Ecological Observatory Network (NEON) and format them into
  standardized, reproducible datasets.

## How to Build One

Building an effective agentic workflow for environmental or ecological modeling
follows a structured lifecycle:

1. Decompose the Workflow: Break your research process (e.g., gathering
   observations, data cleaning, analysis, visualization) into distinct logical
   tasks.

2. Assign Agents: Create specialized single-responsibility agents for each
   task.Equip Tools: Connect your agents to the relevant databases (e.g., GBIF,
   NOAA) and languages (Python/R) using frameworks like LangGraph or Gumloop.

3. Implement Guardrails: Enforce deterministic validation points so that agents
   cannot perform irreversible actions (like minting DOIs or altering central
   databases) without human-in-the-loop oversight.

You can explore resources and templates on data harmonization and multi-agent
systems directly through the CU-ESIIL GitHub Repository.

## Response 5:

That means the scaffold needs to handle three distinct content types cleanly:
prose, data, and code. Here's a draft general template structure:

```
project-name/
├── docs/
│ ├── YYYY-MM-DD_session-notes.md
│ └── README.md
├── writing/
│ └── (source .md files → rendered docx/pdf for sharing)
├── data/
│ ├── raw/ (original files, never modified)
│ └── processed/ (cleaned outputs)
├── scripts/
│ ├── r/
│ └── python/
├── outputs/ │ └── (figures, tables, rendered documents)
├── scratch/ (gitignored)
├── WATERSHED.md
└── .gitignore
```

**The key decisions baked in:**

`raw/` is read-only by convention — agents and scripts never write there
`writing/` is the source-of-truth for prose; outputs/ holds the renders
`scratch/` absorbs exploratory work that doesn't belong in version control
`WATERSHED.md` lives at root so it's always findable

**What this doesn't solve yet:** where your existing messy files land during
migration. That's a triage step — sorting backlog items into this structure —
which is a good candidate for a simple agentic task once the scaffold exists.

Does this structure conflict with anything in how your current projects are
